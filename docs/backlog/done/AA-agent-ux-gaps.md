# 백로그 AA — 에이전트 사용성 격차 + 목적적합성 실행 중 발견된 버그 🔍

> 상태: 🔲 미착수 (2026-06-21 기록)
> 출처: 백로그 Z(목적 적합성 검증) S1~S7 실행 중 사용자 직접 관찰 + 산출물 대조 검증으로 발견.
> 목적: Codex/Claude Cowork류 범용 에이전트 UX와 비교했을 때 부족한 점, 그리고 실행 중 드러난 실제 버그를 한곳에 모아 우선순위를 매긴다.

## 우선순위 P0 — 신뢰성 버그(조용한 실패)

### AA-1. `office_com` Excel 저장 결과물이 손상된 zip으로 저장됨 (silent corruption) 🔴
- **증상**: `excel_set_cells`로 `배치기록.xlsx`의 A4/D4/E4를 수정 후 저장. 에이전트는 "처리 완료"로 정확한 셀 값까지 보고했고 Obsidian 기록에도 "실행 완료"로 적음.
- **실측 검증**: 저장된 `배치기록.xlsx`를 `zipfile`/`unzip -l`로 열면 **"End-of-central-directory signature not found"** — 유효한 zip이 아님(EOCD 레코드 없음). 반면 같은 경로에 자동 생성된 백업(`*.bak`, 수정 전 원본)은 정상 zip으로 열림.
- **의미**: COM이 `Save()` 호출에서 에러를 던지지 않았기 때문에 에이전트는 성공으로 보고했지만, 실제 출력 파일은 손상되어 **Excel로도 다시 열리지 않을 가능성이 높음**. 에이전트의 self-report가 COM API 리턴값만 신뢰하고 **출력 파일 자체의 무결성을 검증하지 않는다**는 구조적 결함.
- **재현 추정 원인(확인 필요)**: ① 네트워크/동기화 드라이브 경로에 COM이 저장 중 핸들을 늦게 플러시, ② office_com 저장 직후 파일을 다른 프로세스(백업 로직?)가 다시 손대며 잘림, ③ COM `SaveAs` 포맷 파라미터 불일치.
- **권장 조치**: `office_com.py`의 Excel/PPT 저장 경로에 **저장 직후 무결성 검사**(`zipfile.is_zipfile()` 또는 재오픈 검증)를 추가하고, 실패 시 에이전트에게 "저장은 호출됐지만 결과 파일이 손상됨"으로 정확히 환류. 백로그 V(타임아웃)와 유사하게 **신뢰 가능한 완료 신호** 설계가 필요.
- **심각도**: 최고 — GxP 문서 편집에서 "성공했다고 보고했지만 실제로는 파일이 깨짐"은 가장 위험한 실패 유형(백로그 Z의 평가척도 "실패" 중 최악 케이스).

### AA-2. `ppt_replace_text` 의존성 누락 — 런타임에 `No module named pptx` 🟠
- **증상**: PPT 텍스트 교체 시도 시 도구가 `python-pptx` 모듈을 찾지 못해 실패.
- **긍정적 측면**: 에이전트가 이 실패를 **숨기지 않고 정직하게 보고**했고("PPT 자동 수정은 도구 오류로 실패"), 거짓 성공을 주장하지 않았다 — S6(보고 정확성) 관점에서는 모범적 동작.
- **권장 조치**: `requirements.txt`에 `python-pptx`가 명시돼 있는지, 실제 배포 conda 환경에 설치돼 있는지 확인. `office_com.py`의 PPT 경로가 COM 우선이어야 하는데 폴백(python-pptx)으로 빠진 경로/조건 점검.

## 우선순위 P1 — 실행 가시성/투명성

### AA-3. PPT 편집 작업 중 화면에 아무것도 보여주지 않음
- 사용자 관찰: "ppt를 편집하는 것 같은데, 화면에 보여주질 않아서 뭔 작업을 하는지 모르겠음."
- Excel 단계에서는 Excel 창이 실제로 열려 진행을 눈으로 볼 수 있었던 반면, PPT 단계는 COM 실패 후 폴백 경로로 빠지며 **어떤 창도 뜨지 않고 로그 패널 텍스트로만 진행이 표시**됨.
- Codex/Claude Cowork 대비 격차: 도구가 실패하거나 폴백으로 전환될 때 "지금 무엇을 시도 중인지"를 사용자가 알아챌 신호가 약함.
- 권장 조치: `_intent_label`(백로그 S) 수준을 넘어, 폴백 전환 시점("COM 실패 → python-pptx로 재시도")을 명시적 SSE 텍스트로 내레이션.

### AA-4. 진행 상황 설명이 빈약함
- 사용자 관찰: "진행사항에 대한 설명이 약간 부족해 보임."
- 백로그 S(의도 라벨)·V(TOOL_WAIT 내레이션)가 이미 구현돼 있으나, 실제 체감상 "지금 단계 / 왜 이 단계인지 / 다음에 뭘 할지"에 대한 한 줄 요약이 충분치 않음.
- 권장 조치: 워크플로우 패널의 단계 카드 설명을 더 구체화하거나, 매 도구 호출 전 1줄 "왜 이 작업을 하는지" 텍스트를 모델에 강제(prompt 차원).

### AA-5. 채팅창이 진행 중 계속 아래로 스크롤되어 진행상황 파악이 어려움
- 사용자 관찰: "자꾸 화면이 내려가버려서 진행사항 파악이 어려움."
- CLAUDE.md에는 이미 "채팅 강제 자동스크롤 버그픽스"(`isNearBottom()` 게이트)가 완료 항목으로 기록돼 있음 — 그런데 이번 실행에서도 동일 증상이 재현됨. **회귀(regression) 가능성** 또는 우측 워크플로우 패널/HUD 갱신이 별도 경로로 스크롤을 강제하는 경우가 있는지 재조사 필요.
- 권장 조치: `scroll-utils.js`의 게이트가 이번 시나리오(연속 confirm 다이얼로그 + 우측 패널 갱신)에서도 실제로 적용되는지 재현 테스트. 회귀라면 P0로 재분류.

## 우선순위 P2 — 워크플로우/스레드 온보딩

### AA-6. 새 업무를 시작할 때 새 스레드를 만들지 않고 기존 열린 스레드에서 바로 진행됨
- 사용자 관찰: "테스트를 하는데, 새로운 업무를 만들지않고 기존에 떠있던 창에서 바로 시작해 버림."
- 이번 검증 중 직접 겪은 문제와 동일: CLAUDE.md UI 명세상 "+새 시작" 버튼이 있어야 하는데, 사이드바에서 반복 클릭해도 스레드 목록 접기/펼치기만 토글되고 새 스레드 생성 버튼을 찾지 못해 기존 스레드("기본업무 06/20 #001")에서 그대로 진행함.
- 영향: 기존 스레드에 남아있던 무관한 대화(이전 유튜브 관련 대화 등)가 컨텍스트에 섞일 위험 — 목적적합성 검증 자체의 신뢰도에도 영향.
- 권장 조치: "+새 시작" 버튼의 실제 클릭 가능 좌표/표시 여부를 UI 레벨에서 재확인(렌더링 안 됨 vs 위치만 다름). 신규 사용자가 직관적으로 못 찾는다면 버튼 가시성 자체를 개선.

## 우선순위 P3 — 다중 확인창(Confirm) UX 혼란

### AA-7. 동일하게 생긴 G3 확인창이 연속으로 여러 번 스택되어, 사용자가 "한 번 눌렀는데 왜 또 뜨나" 혼란
- 실측: `ppt_replace_text`에 대해 내용이 다른 확인창(① 모델의 사전 확인 "내용을 이렇게 바꾸려는데 진행할까요" ② G3 안전게이트의 범용 확인 "시스템/데이터를 변경할 수 있습니다")이 **시각적으로 거의 동일한 모달 스타일**로 연속 등장 — 사용자가 같은 다이얼로그가 안 닫히는 것으로 오인하기 쉬움.
- 사용자 직접 지적: "허용 한 번 누르면 될 것 같은데 캡처를 몇 번하는거야?"
- 권장 조치: ① 모델의 사전확인(ask_user)과 ② G3 안전게이트 확인을 **시각적으로 구분**(타이틀/색상/아이콘 다르게) — 같은 작업에 대해 두 단계 확인이 필요한 이유를 사용자가 즉시 알 수 있게.

## Codex / Claude Cowork 대비 종합 격차 (우선순위순)

1. **결과 무결성 검증 부재**(AA-1) — Cowork/Codex류는 파일 쓰기 후 보통 결과를 재확인하거나 최소한 실패를 정확히 표면화한다. MES Agent는 COM 리턴값만 믿는다.
2. **실행 가시성**(AA-3, AA-4) — Cowork는 매 도구 호출 전후 "무엇을 왜 하는지"가 텍스트로 명확히 나온다. MES Agent는 로그가 있지만 해석 부담이 사용자에게 넘어간다.
3. **신규 작업 시작 UX**(AA-6) — Cowork/Codex는 새 대화/새 작업 시작이 항상 명확한 단일 진입점이다.
4. **확인창 구분**(AA-7) — Cowork는 위험도별 확인 UI가 명확히 다른 톤으로 구분된다.
5. **스크롤 UX**(AA-5) — 이미 한 번 고친 이력이 있는 만큼 회귀 여부 확인이 우선.
