## 1. 진입점과 초기 상태

- 공개 진입점은 `async function* query(...)` (L222). 곧바로 `const terminal = yield* queryLoop(params, consumedCommandUuids)` (L233)로 위임한다. 즉 **루프 본체는 `queryLoop`** (L244)이고, `query`는 얇은 래퍼다.
- `queryLoop`은 **불변 `params`** 를 구조분해한다 (L256):

  ```ts
  const { systemPrompt, userContext, systemContext, canUseTool,
          fallbackModel, querySource, maxTurns, skipCacheWrite } = params
  ```

  여기서 "루프를 시작시키는 인자"는 사실상 `params.messages`(초기 대화), `params.toolUseContext`(도구·옵션·abort 신호·앱상태 접근자 묶음), `systemPrompt`, `maxTurns`, `canUseTool`(권한 콜백), `fallbackModel`이다. cwd/설정은 `toolUseContext.options`와 `getAppState()`를 통해 간접 접근한다.
- **최초 실행상태**는 단일 `state` 객체로 셋업된다 (L271): `messages=params.messages`, `toolUseContext=params.toolUseContext`, `turnCount=1`, `continuationNudgeCount=0`, `maxOutputTokensRecoveryCount=0`, `hasAttemptedReactiveCompact=false`, `autoCompactTracking=undefined` 등.
- 진입 직후 `config = buildQueryConfig()`로 세션/게이트 스냅샷을 한 번 고정하고, `startRelevantMemoryPrefetch(...)`를 `using`으로 1회 발사(턴마다 반복 안 함, L305) 한 뒤 `while (true)`(L311) 루프에 진입한다.
- 출처: `[openclaude query.ts]` L222–L311.

## 2. 루프 1회전 해부

한 회전은 **(a) 컨텍스트 조립 → (b) 모델 호출 → (c) 응답 분기 → (d) 결과 환류** 순서다.

**(a) 컨텍스트/메시지 조립.** 매 회전 첫머리에서 `state`를 구조분해(L312)한 뒤, 컨텍스트 압축을 *순서대로* 적용해 `messagesForQuery`를 만든다: `snip`(L406) → `microcompact`(L424, `messagesForQuery = microcompactResult.messages`) → `autocompact`(L463). 압축은 "읽기 시점 투영"이라 원본 `messages`를 파괴하지 않고, 일부는 boundary 메시지를 `yield`한다. 이 단계가 mes-agent의 "컨텍스트 사용량/슬라이딩 윈도우"에 대응한다.

**(b) 모델 요청 형태.** 실제 호출은 `deps.callModel({...})`를 `for await`로 스트리밍한다 (L692):

```ts
for await (const message of deps.callModel({
  messages: prependUserContext(messagesForQuery, userContext),
  systemPrompt: fullSystemPrompt, tools: toolUseContext.options.tools,
  signal: toolUseContext.abortController.signal, options: { ... },
})) { ... }
```

핵심 파라미터: `messages`(압축된 대화+유저컨텍스트 선두삽입), `systemPrompt`, `tools`(도구 스키마 목록), `signal`(취소), 그리고 `options`(모델명·fallbackModel·`getToolPermissionContext()`·thinkingConfig·maxOutputTokensOverride·mcpTools 등). **스트리밍**이라 메시지가 토막으로 도착한다.

**(c) 응답 분기 (텍스트 vs tool_call).** 도착한 `message.type`으로 가른다 (L860):

```ts
if (message.type === 'assistant') {
  assistantMessages.push(message)
  const msgToolUseBlocks = message.message.content.filter(c => c.type === 'tool_use')
  if (msgToolUseBlocks.length > 0) { toolUseBlocks.push(...); needsFollowUp = true }
}
```

즉 **분기 기준은 stop_reason 문자열이 아니라 assistant 콘텐츠 안에 `type:'tool_use'` 블록이 있느냐**다. 있으면 `needsFollowUp=true`(도구 실행 후 한 번 더 모델에 물어봐야 함), 없고 텍스트뿐이면 종료 경로(§4의 `completed`/continuation nudge)로 흐른다.

**(d) tool_call 파싱 → 디스패치 → 결과 포맷 → 환류.** `tool_use` 블록을 `toolUseBlocks`에 모은 뒤(§3), 실행 결과를 `normalizeMessagesForAPI(...)`로 `type:'user'`의 `tool_result` 메시지로 정규화해 `toolResults`에 push한다 (L1503). 다음 회전 재요청 시 누적 메시지로 합쳐 보낸다 (L1824):

```ts
messages: [...messagesForQuery, ...assistantMessages, ...toolResults]
```

이 "assistant(도구호출) → user(tool_result) → 다음 모델 호출" 환류가 에이전트 루프의 심장이다.
- 출처: `[openclaude query.ts]` L312–L463, L692, L860–L897, L1490–L1516, L1824.

## 3. 다중 tool_call 처리

- 한 assistant 메시지가 여러 `tool_use` 블록을 담으면 모두 `toolUseBlocks`에 누적된다 (L863–L867).
- 실행 경로는 두 갈래다 (L1488):

  ```ts
  const toolUpdates = streamingToolExecutor
    ? streamingToolExecutor.getRemainingResults()
    : runTools(toolUseBlocks, assistantMessages, canUseTool, toolUseContext)
  ```

  - **streaming 경로**: 스트리밍 도중 블록이 도착할 때마다 `streamingToolExecutor.addTool(toolBlock, message)`로 *즉시* 실행을 시작(L875)하고, 완료분을 `getCompletedResults()`로 흘려보낸다(L885).
  - **일괄 경로**: 스트리밍 종료 후 `runTools(...)`가 블록 묶음을 실행한다.
- 어느 경로든 결과는 `for await (const update of toolUpdates)`로 받아 **도착 순서대로** `toolResults`에 push (L1492–L1516)된다. 실패/거부도 동일 채널로 `tool_result`(에러 표시)가 흘러나와 다음 모델 호출에 환류된다.
- **순서·실패 처리 주의점**: 각 `tool_use`에는 고유 `id`가 있고, 모델 API는 *모든* `tool_use`에 대응하는 `tool_result`가 짝을 이뤄야 한다. 그래서 abort/fallback 등으로 중간 이탈 시 `yieldMissingToolResultBlocks(...)`(L121, L1015)가 **누락된 tool_result를 합성**해 짝을 맞춘다(불변조건 보호).
- **확인 필요(→§11)**: `runTools` 내부가 직렬인지 병렬(동시성 제한)인지의 정확한 정책은 `query.ts`만으로는 단정 불가.
- 출처: `[openclaude query.ts]` L863–L897, L1015, L1488–L1516.

## 4. 종료조건 (가장 중요)

`queryLoop`은 `Terminal` 객체 `{ reason: ... }`를 **return** 하며 끝난다. 관찰된 reason 값과 발동 조건:

| reason | 발동 조건 | 위치 |
|---|---|---|
| `completed` | 모델이 `tool_use` 없이 응답을 끝냄(정상 종료). continuation nudge가 불필요·소진된 경우 포함. | L1299, L1465 |
| `max_turns` | `maxTurns && nextTurnCount > maxTurns` — 턴 상한 초과. 반환 객체에 `turnCount` 동봉. | L1813–L1819 |
| `aborted_streaming` | 모델 스트리밍 도중 abort 신호. | L1082 |
| `aborted_tools` | 도구 실행 도중 abort 신호(가장 흔한 Ctrl+C 경로). 반환 전 maxTurns 초과면 안내 메시지 yield. | L1614–L1623 |
| `model_error` | `callModel` try/catch가 잡은 일반 런타임/모델 오류. `error` 동봉. | L1027 |
| `image_error` | 이미지 크기/리사이즈 오류. | L1008 |
| `prompt_too_long` | 컨텍스트가 한도 초과(회복 불가 확정 시). | L1208, L1215 |
| `stop_hook_prevented` | Stop 훅이 종료를 가로막아 정지. | L1314 |
| `hook_stopped` | 도구 결과의 `hook_stopped_continuation` 어태치먼트로 계속 진행 차단. | L1628 |

**계속 vs 종료의 분기 핵심:**
- `tool_use`가 있으면 → 도구 실행 후 **계속**(다음 회전).
- `tool_use`가 없으면 → 기본 **종료(`completed`)**. 단 **continuation nudge**(L1398–L1465): 모델이 도구 없이 멈췄어도 `assistantMessages.length>0 && turnCount < (maxTurns ?? Infinity) && continuationNudgeCount < MAX_CONTINUATION_NUDGES` 면, "계속하라"는 nudge 메시지를 주입하고 루프를 더 돈다(무한루프 방지로 `MAX_CONTINUATION_NUDGES` 상한). 한도 도달 시 `completed`.
- **빈 응답/예외**: 모델 호출이 throw하면 합성 tool_result로 짝 맞춘 뒤(L1015) `model_error` 반환. fallback 가능 오류는 종료가 아니라 §7의 재시도로 흡수.
- 출처: `[openclaude query.ts]` L1008, L1027, L1082, L1208–L1215, L1299, L1314, L1398–L1465, L1614–L1628, L1813–L1819.

## 5. 상태 모델 (정의 vs 실행상태 — C3 관점)

**불변(정의) — `params`** (루프 내 절대 재할당 안 됨, 주석 L255 "Immutable params — never reassigned"):
`systemPrompt`, `tools`(via `toolUseContext.options.tools`), `canUseTool`, `maxTurns`, `fallbackModel`, `querySource`, `skipCacheWrite`. → "요청 한 번을 *어떻게* 구성할지"의 규칙·상한.

**가변(실행상태) — `state`** (L271, 매 회전 top에서 구조분해, continue 지점마다 `state = {...}`로 일괄 갱신):
`messages`(누적 대화), `turnCount`, `continuationNudgeCount`, `maxOutputTokensRecoveryCount`, `hasAttemptedReactiveCompact`, `autoCompactTracking`, `toolUseContext`(회전 내 `queryTracking`·메시지 갱신으로 *유일하게* 회전 중 재할당됨, L315). 회전 단위 임시 누적: `assistantMessages`, `toolResults`, `toolUseBlocks`, `taskBudgetRemaining`(루프-로컬, compaction 경계 넘는 예산 추적, L295).

**C3 경계 메모**: 코드가 *의도적으로* `params`(정의) ↔ `state`(실행상태)를 분리해 두었다(주석이 이를 명시). "정의 = 도구목록·시스템프롬프트·턴/토큰 상한" vs "실행상태 = 지금까지 쌓인 메시지·턴 수·예산 잔량". mes-agent에는 이미 `WorkflowDefinition`(불변) vs `RunState`(가변, `*_state.json`)의 동형 분리가 있으므로, L1 포팅은 이 경계를 그대로 계승하면 된다.
- 출처: `[openclaude query.ts]` L255–L295, L312–L315.

## 6. 권한 게이트 지점 (우리 APPROVE1 삽입점)

**존재한다.** 도구 실행 "직전"에 호출되는 권한 콜백 `canUseTool`이 그 지점이다.

- 시그니처(소비처에서 주입): `canUseTool(tool, input, toolUseContext, assistantMessage, toolUseID, forceDecision)` → `{ behavior: 'allow' | ... }` 반환.
- `runTools(toolUseBlocks, assistantMessages, canUseTool, toolUseContext)` (L1490)에 콜백이 전달되어, **각 `tool_use` 블록마다 실행 전 호출**된다. `behavior !== 'allow'`면 그 도구는 거부되고 거부용 `tool_result`가 환류된다.
- `[openclaude QueryEngine.ts]` L245의 `wrappedCanUseTool`이 원 콜백을 감싸 거부를 집계한다:

  ```ts
  const result = await canUseTool(tool, input, toolUseContext, assistantMessage, toolUseID, forceDecision)
  if (result.behavior !== 'allow') {
    this.permissionDenials.push({ tool_name: ..., tool_use_id: toolUseID, tool_input: input })
  }
  ```

- `[openclaude Tool.ts]` L249 주석: "canUseTool must always be called even when hooks auto-approve" — 자동승인 훅이 있어도 권한 콜백은 **항상** 통과시킨다(게이트 우회 금지).

→ **mes-agent APPROVE1 = 위험 activity를 디스패치하기 직전, 바로 이 `canUseTool` 위치에 사내 확인 훅(예: `_safety.py` 가드 + 사용자 `ask_user` 확인)을 끼운다.** 구조적으로 이미 "도구별·실행직전" 후크 포인트가 마련돼 있어 삽입이 자연스럽다.
- 출처: `[openclaude query.ts]` L1490; `[openclaude QueryEngine.ts]` L245–L272; `[openclaude Tool.ts]` L249.

## 7. 에러·리트라이 (REFACTOR_BRIEF C2/X1 메모)

루프 내부에 **종료가 아닌 회복** 경로가 여러 겹 있다:

- **모델 fallback**: `FallbackTriggeredError`를 잡으면 `currentModel = fallbackModel`로 바꾸고, 진행 중 assistant/tool 상태를 비운 뒤 `continue`로 **같은 회전을 재시도**한다(L928–L982). 사용자에게는 경고 시스템 메시지만 yield.
- **출력토큰 상한 회복**: `maxOutputTokensRecoveryCount < MAX_OUTPUT_TOKENS_RECOVERY_LIMIT`이면 상한을 `ESCALATED_MAX_TOKENS`로 올려 재시도(L1235–L1257). 한도 소진 시에야 포기.
- **컨텍스트 회복**: reactive compact / collapse / truncation 재시도로 `prompt_too_long`을 흡수하려 시도하고, 실패 확정 시에만 종료(L822–L856, L1208).
- **일반 오류**: 위 회복에 안 걸리면 try/catch가 로깅 후 합성 tool_result로 짝을 맞추고 `model_error` 반환(L986–L1027).

C2/X1 번역 메모: 이들은 "전역 재시도"가 아니라 **오류 종류별 차등 정책**(모델교체 / 상한상향 / 압축 / 포기)이다. mes-agent로 옮길 때 UiPath식 *activity별 리트라이 정책*(C2)으로 일반화하고, 회복 한도(`*_RECOVERY_LIMIT`, `MAX_CONTINUATION_NUDGES`)는 무한루프 방지 불변조건으로 보존한다.
- 출처: `[openclaude query.ts]` L822–L856, L928–L982, L1235–L1257, L986–L1027.

## 8. 버릴 것 (코딩/CLI 특화 — mes-agent 불필요)

다음은 claw-code/openclaude가 "코딩 에이전트 + 호스트 CLI"이기 때문에 존재하며, 업무자동화 mes-agent에는 **버린다**:

- **코딩 전용 도구**: file/edit/glob/grep/bash 류(루프 자체가 아니라 도구 카탈로그 쪽). 그 자리에 MES 화면조작/이미지·차트 인식/Obsidian 기록 activity가 들어간다.
- **thinking-block 서명·프롬프트 캐시 바이트 정합** 처리(L776–L821, L958–L961): 특정 모델군의 캐싱/서명 제약. 사내 OpenAI호환 LLM엔 불필요(또는 단순화).
- **MCP 도구 풀·pending 서버**(`appState.mcp.*`, L722–L725): 외부 MCP 생태계 연동. 폐쇄망 기본 시나리오에선 버림/선택.
- **VCR fixture·텔레메트리**(`tengu_*` 이벤트, `logEvent`, queryChainId/Depth): 분석/회귀 인프라. 버림.
- **tool_use_summary(Haiku 호출)**(L1519–L1590), **continuation nudge 텍스트**, **streamingFallback tombstone**(L746–L775): 호스트 UX/내부최적화. 핵심 루프 불변조건이 아니므로 1차 포팅에서 제외.

> 가져올 것(§2·§3·§5)과의 구분: **루프 골격(모델호출→tool_use 분기→실행→tool_result 환류→종료사유), 권한 콜백(§6), 정의/실행상태 분리(§5), 회복 한도(§7)** = 가져온다. 위 목록 = 버린다.

| openclaude(코딩 루프) | mes-agent(업무 자동화) |
|---|---|
| `deps.callModel({messages, tools, ...})` | 사내 OpenAI호환 LLM 호출 (`agent/llm.py`, `get_model()` 오버라이드) |
| `tool_use` 블록 | **activity** — MES 화면 클릭/OCR/이미지매칭(`screen.py`,`desktop.py`), 문서/Obsidian 기록(`document.py`,`obsidian_rag.py`) |
| `tool_result` 환류 | activity 실행결과(JSON) → 다음 LLM 호출 메시지 |
| `canUseTool` 권한 콜백 | 사내 권한 티어 + 파괴적작업 가드(`agent/tools/_safety.py`), 필요시 `ask_user` 확인 |
| compaction(micro/auto/snip) | 컨텍스트 사용량 바 + 슬라이딩 윈도/요약(서버 `generate()`) |
| `maxTurns` / continuation nudge | `_MAX_STEPS`(현 40) / 단계상한 도달 시 '계속' 안내 |
| `params`(정의) vs `state`(실행) | `WorkflowDefinition`(불변) vs `RunState`(가변 `*_state.json`) |
| `Terminal{reason}` | 워크플로우 단계 상태(done/error) + SSE `DONE`/`ERROR` |

## 10. PLAN1 / APPROVE1 삽입점

- **PLAN1 (실행계획 DAG를 "정의로만" 캡처)**: 첫 모델 응답에서 `tool_use` 블록을 추출하는 직후 지점(L863, `msgToolUseBlocks` 산출 직후)이 분기점이다. 여기서 *즉시 실행*하는 대신 블록 묶음을 `WorkflowDefinition`(노드·연결)으로 적재하면, "계획 먼저 → 승인 → 실행"의 mes-agent 워크플로우 모델과 맞물린다. 즉 **루프의 tool_use 추출 ↔ 도구 실행 사이**가 PLAN1 삽입선.
- **APPROVE1 (위험 activity 직전 일시정지)**: §6의 `canUseTool` 콜백 위치(`runTools` 내부, 각 블록 실행 직전). 이미 "도구별·실행직전" 후크라 위험도 판정 → 일시정지 → 사용자 승인(`ask_user`) → 재개를 그대로 끼울 수 있다.
- 두 지점은 인접한다: **추출(PLAN1) → 권한판정/승인(APPROVE1) → 실행 → tool_result 환류**.

## 11. 미해결 / 모호 (소스만으로 단정 불가)

1. **`runTools` 동시성 정책**: 여러 `tool_use`를 직렬 실행하는지, 동시성 제한 병렬인지, 읽기/쓰기 안전성 기준으로 가르는지 — `query.ts`엔 호출부만 있고 본체 미확인(`tools.ts`/`Tool.ts` 추가 관찰 필요).
2. **stop_reason → reason 매핑 위치**: 모델 API의 raw `stop_reason`(end_turn/tool_use/max_tokens 등)이 어디서 루프의 `Terminal.reason`으로 환산되는지. 본 루프는 stop_reason 문자열보다 *콘텐츠에 tool_use 유무*로 분기하므로, 원시 stop_reason 처리는 `callModel`/`QueryEngine` 내부에 있을 가능성(미정독).
3. **streamingToolExecutor 선택 조건**: 어떤 경우 스트리밍 실행기가 켜지고(L692 분기) 어떤 경우 일괄 `runTools`로 떨어지는지의 게이트 조건.
4. **taskBudget 세부**: `taskBudgetRemaining`이 compaction 경계마다 어떻게 차감되는지(주석은 server-side 카운트다운 언급, 클라이언트 측 계산식 일부만 노출).
5. **claw-code Python 미러와의 정합**: 미러의 `completed`/`max_turns_reached`/`max_budget_reached` 3종이 본 원본의 다종 reason을 어디까지 단순화했는지는 페이즈 B에서 대조 필요.

> 위 1·2는 페이즈 B(계약서) 작성 전 `tools.ts`/`QueryEngine.ts` 추가 관찰로 해소 권장. 본 L1 관찰의 **핵심(진입점·1회전 해부·종료사유·상태분리·권한게이트·삽입점)** 은 확정되었다.
