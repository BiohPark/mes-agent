# 인수인계 — mes-agent L1 루프 개선

## 목표
mes-agent(사내 폐쇄망 업무자동화 에이전트)의 실행 루프를 "강한 에이전트급
문제해결력"으로 끌어올린다. 루프를 새로 만들지 않고, 있는 것을 개선한다.

## 환경/제약
- Python 3.11/conda, FastAPI(agent/server.py) + Electron UI. 사내 로컬 LLM(OpenAI 호환).
- 개발은 회사 밖에서, 결과를 폐쇄망 PC로 git pull. 런타임에 외부 네트워크 호출 금지.
- pytest는 환경에 포함돼야 함(과거 누락 이슈). 설치는 사람이 직접.
- 테스트 실행: `.\test.ps1` 또는 `python -m pytest -q`. 현재 **374 passed, 1 skipped**.

## 현재 루프 (agent/server.py: generate())
OpenAI 스타일 스트리밍 tool-calling 루프. 이미 있는 것:
- 자동 디스커버리 툴 레지스트리(MANIFEST), `_MAX_STEPS=40`, `_CONTEXT_MAX_TOKENS=128_000`
- 확인 팝업 골격: `ask_user`의 `__confirm__` → CONFIRM SSE → `asyncio.Event` → `/confirm`.
  공통 헬퍼 `_resolve_confirm(cid)`로 일원화됨(타임아웃=거부).
- 정의 vs 실행상태 분리: WorkflowDefinition ↔ WorkflowRunState(set_node_status)
- 단계별 재시도: 워크플로 step `max_retry` 기반
- 안전 모듈 `agent/tools/_safety.py`
- **G3 중앙 안전 게이트(신규, 완료)**: `run_tool` 직전 `classify_risk`로 강제. (아래)

## 4가지 격차 진행상황 (docs/contracts/L1_loop_contract.md에 상세)

- **G3 (1순위) 안전 게이트 — ✅ 완료(2026-06-10)**
  - `_safety.classify_risk(tool_name,args,allowlist)→safe|mutate|destructive`.
  - `server.generate()`가 `run_tool` 직전에 호출해 강제(모델 force 우회 불가).
    safe→즉시, mutate/destructive→CONFIRM 팝업(예/항상/아니오)→`_resolve_confirm`.
    "항상"→`_session_allowlists`, 거부/타임아웃→미실행+사유 환류(짝 보존).
  - 균형형: 읽기·관찰·입력형=safe, 쓰기·삭제·셸변경·office편집·네트워크만 확인.
  - 테스트: `tests/unit/test_safety.py`(classify_risk), `tests/integration/test_server_chat.py::TestSafetyGate`.

- **G1 (현재 작업) compaction** — 계약 §4 참조.
  - 현재 `_estimate_tokens`(server.py L133)는 사용량 **표시만** 한다.
  - 임계치(`_CONTEXT_MAX_TOKENS * COMPACT_RATIO`, 예 0.8) 초과 시: system 메시지(들)와
    **최근 N턴 보존**, 그 사이 오래된 메시지를 동일 로컬 LLM(`get_client`) 요약 1개로 치환.
  - **핵심 불변조건(I1)**: `tool_calls` ↔ `tool`(tool_call_id) **짝을 깨면 안 됨**(OpenAI 제약).
    짝 단위로만 제거/요약. 떠도는 tool 메시지 금지.
  - 압축 시 `COMPACTION` SSE로 사용자 고지. `compaction_count` 상한으로 무한압축 방지.

- **G2 continuation nudge** — 🔲 대기. `finish_reason!=tool_calls`면 즉시 종료 → 미완 시 한도 내 '계속' 주입.
- **G4 plan 모드(PLAN1)** — 🔲 대기. auto/plan 스위치. plan은 WorkflowDefinition 먼저 생성→승인→실행.

### 코드 앵커 (agent/server.py, G3 반영 후 기준 — 변동 가능하니 마커로 확인)
- `_estimate_tokens(messages)` — **L133** (글자수/4 추정).
- `_MAX_STEPS=40`, `_CONTEXT_MAX_TOKENS=128_000` — **L169–170**.
- 메인 루프 `for _step in range(_MAX_STEPS):` — **L210**.
- 사용량 emit `tokens_used = _estimate_tokens(messages)` — **L217**.
- 모델 호출 `client.chat.completions.create(...)` — **L230**.
- 삽입 위치: 루프 본문 맨 위(중단확인 직후), **사용량 emit(L217) 직전** → 압축 후 사용량이 반영되게.

### 구현 스케치
- 상수: `COMPACT_RATIO=0.8`, `COMPACT_KEEP_RECENT`(예 6), `MAX_COMPACT`(예 3), `_compaction_count` 실행상태.
- `_estimate_tokens(messages) > _CONTEXT_MAX_TOKENS*COMPACT_RATIO` 이고 `compaction_count<MAX_COMPACT`면:
  1. system 메시지(들) + 최근 N개 메시지 분리(보존).
  2. 중간 구간을 요약: `get_client().chat.completions.create(stream=False)`로
     "진행/결정/미해결 ≤500토큰 요약" → `{"role":"system","content":"[이전 진행 요약]\n..."}` 1개로 치환.
  3. **짝 보존**: 보존/제거 경계가 `assistant(tool_calls)`와 그 `tool` 결과 사이를 가르지 않도록
     경계를 조정(짝 단위로 잘라낸다). 요약 후에도 떠도는 tool 메시지가 없어야 함.
  4. `COMPACTION` SSE emit, `compaction_count++`. 요약조차 한도 초과면 가장 오래된 tool 결과부터 truncate.
- `agent/core/events.py`에 `COMPACTION = "compaction"` 추가(additive). 프론트는 선택적으로 안내 표시.

### 테스트 (먼저 작성, 패턴은 기존 것 재사용)
- `tests/unit/`: 압축 순수함수(예 `_compact_messages(messages, keep_recent)`)를 분리해 단위 검증 —
  ① 임계 미만이면 그대로, ② 초과면 길이 감소, ③ **system 보존**, ④ **최근 N턴 보존**,
  ⑤ **tool_calls↔tool 짝 정합 유지**(I1), ⑥ `MAX_COMPACT` 상한(I3).
  요약 LLM은 monkeypatch로 가짜 요약 반환(`get_client`). 순수함수로 빼면 LLM 없이도 짝/보존 로직 검증 가능.
- `tests/integration/test_server_chat.py`: 긴 메시지 누적 시 `COMPACTION` SSE가 뜨고, 이후 정상 `DONE`까지
  마감되는지(I4). `_ScriptedStream`/`FakeLLMClient` 패턴 재사용, `_CONTEXT_MAX_TOKENS`/`COMPACT_RATIO` monkeypatch로 임계 낮춰 트리거.
- 신규 툴 없음 → `tests/smoke/test_tool_schemas.py::EXPECTED_TOOL_COUNT`(127) 변경 불필요.
